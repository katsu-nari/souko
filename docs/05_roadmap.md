## 3. フェーズ間依存関係

```
凡例: → 依存する（前のフェーズ完了が必要）
      ⇢ 部分的に依存（特定タスクのみ）

Phase 1（収容量・操作性）
    │
    ├→ Phase 2（通路検出・レイヤー）
    │       │
    │       ├→ Phase 3（障害物考慮自動配置）
    │       │       │
    │       │       ⇢ Phase 4（ゾーン管理）
    │       │               │
    │       │               ├→ Phase 5（提案書生成）
    │       │               │       │
    │       │               │       ⇢ Phase 6（AI提案）
    │       │               │               │
    │       │               │               ⇢ Phase 7（ROI試算）
    │       │               │               │
    │       │               │               ⇢ Phase 8（動線シミュ）
    │       │               │                       │
    │       │               └───────────────────── Phase 9（多拠点）
    │       │
    └───────┴─（並列実施可能）
```

### 必須依存関係

| フェーズ | 依存するフェーズ | 理由 |
|---------|--------------|------|
| Phase 2 | Phase 1 | アイテム構造（params, layerId）の追加が必要 |
| Phase 3 | Phase 2 | 通路幅検出アルゴリズムを自動配置時の通路確保に転用 |
| Phase 4 | Phase 2 | レイヤー構造の上にゾーンレイヤーを追加 |
| Phase 5 | Phase 4 | ゾーン面積・収容量データを提案書算出に使用 |
| Phase 6 | Phase 3, Phase 4 | 障害物考慮配置＋ゾーン管理が前提 |
| Phase 9 | Phase 1 | JSON エクスポート構造が確定してから IndexedDB 設計 |

## 4. リスク一覧

### 4.1 技術リスク

| ID | リスク内容 | 発生確率 | 影響度 | 対策 |
|----|----------|---------|-------|------|
| R-T01 | 通路検出アルゴリズムがラック数増加で低速化 | 中 | 高 | Web Worker での非同期処理、デバウンス制御 |
| R-T02 | jsPDF で日本語フォントが正しく出力されない | 高 | 高 | 事前に日本語フォント埋込み（NotoSansJP）を検証 |
| R-T03 | LocalStorage 容量が複雑なレイアウトで上限に達する | 中 | 中 | 圧縮（LZ-string）か早期 IndexedDB 移行 |
| R-T04 | Three.js 3D ビューがラック 1,000 個超でフレームレート低下 | 中 | 低 | LOD（Level of Detail）切替・インスタンシング |
| R-T05 | 単一 HTML ファイルが 5,000 行を超え保守困難 | 高 | 中 | Phase 2 以降でモジュールコメント整理、ESM 検討 |
| R-T06 | AI 配置最適化の計算時間が長い（30 秒以上） | 中 | 中 | タイムアウト設定・プログレスバー表示・中断機能 |

| ID | リスク内容 | 発生確率 | 影響度 | 対策 |

## 6. 技術的負債・リファクタリング計画

### 6.1 現行コードの技術的負債

| 負債 ID | 内容 | 重要度 | 対応時期 |
|--------|------|-------|---------|
| DEBT-01 | 単一ファイル 2,100 行（ビジネスロジック・描画混在） | 高 | Phase 2 |
| DEBT-02 | グローバル変数（APP）への直接参照が全体に散在 | 中 | Phase 2 |
| DEBT-03 | 描画関数 `draw()` が 500 行を超える巨大関数 | 高 | Phase 1 |
| DEBT-04 | エラーハンドリングがほぼなし | 中 | Phase 1 |
| DEBT-05 | イベントリスナーの重複登録リスク | 低 | Phase 2 |
| DEBT-06 | マジックナンバーが多数散在（定数化されていない） | 中 | Phase 1 |

### 6.2 リファクタリング方針

**Phase 1 内に実施:**
- `draw()` 関数を機能別サブ関数に分割（`drawGrid`, `drawItems`, `drawObstacles` 等）
- マジックナンバーを `const CONFIG = {}` に集約
- LocalStorage CRUD を専用関数に切り出し

**Phase 2 内に実施:**
- `// === MODULE: xxx ===` コメントで論理モジュールを明示
- グローバル APP オブジェクトへのアクセスを getter/setter で整理
- エラーハンドリング関数の共通化（`showError`, `showWarning`, `showSuccess`）

**Phase 3 以降:**
- 計算ロジック（CALC モジュール）のテスト可能な純粋関数化
- Web Worker 化（通路検出・自動配置の非同期処理）
