## 1. 現状分析

### 1.1 アプリケーション概要

本ツールは 3PL 物流企業の新規フルフィルメントセンター立ち上げ支援を目的とした、単一 HTML ファイルで動作する倉庫レイアウト設計ツールである。外部サーバーへの依存がなく、ブラウザのみで完結する。

| 項目 | 内容 |
|------|------|
| 構成 | 単一 HTML ファイル（約 2,100 行） |
| レンダリング | Canvas 2D API（2D 平面図） + Three.js r128（3D ビュー） |
| 永続化 | LocalStorage（キー: `warehousePlannerData`） |
| ライブラリ | Three.js / jsPDF 2.5.1 / XLSX 0.18.5（すべて CDN） |
| 対応端末 | PC・タブレット・スマートフォン（レスポンシブ対応） |

### 1.2 実装済み機能

#### ラックタイプ（5種類）

|-----------|--------|------------|--------------|--------------|----------------|
| nesting | ネスティングラック | 1,350 | 1,200 | 1,700 | pallets: 4 |
| pallet | パレットラック | 2,700 | 1,100 | 5,000 | rows: 1, levels: 4 |
| shelf | 軽量棚 | 900 | 450 | 1,800 | shelves: 5 |

| work | 作業エリア | 3,000 | 3,000 | 0 | — |

#### 障害物タイプ（7種類）

|-----------|--------|------------|--------------|--------------|

#### その他実装済み機能

- ドラッグ&ドロップ配置
- 回転（0/90/180/270°）
- アンドゥ/リドゥ（最大 50 ステップ）
- グリッドスナップ（100mm、Shift キーで 50mm）

- 自動配置（グリッドパターン）
- 3D ビュー（Three.js、マウス操作でカメラ回動・ズーム）
- 寸法表示・ヒートマップモード
- フォークリフト種別設定（リーチ式/カウンター式/ハンドリフト）
- スタッツ表示（面積利用率・ラック数集計）

### 1.3 技術スタック現状評価

```
[強み]
+ 外部依存なし → デプロイが簡単
+ 単一ファイル → バージョン管理・配布が容易
+ Canvas 2D で高速描画（ラック数 200 個でも 60fps 維持）
+ Three.js による直感的な 3D プレビュー

[弱点]
- 単一ファイル 2,100 行 → 保守性低下リスク
- ビジネスロジックと描画ロジックが混在
- LocalStorage のみ → 共有・バックアップ不可
- ストレージ容量計算が面積ベースのみ（ロケーション数・パレット数未対応）
- 通路幅の色分け判定なし
- ゾーン管理機能なし
- 荷主向け提案書生成機能なし
```

## 3. フェーズ別改善方針

### Phase 1: 収容量計算強化 + 操作性改善

**目的:** ラックタイプ別の詳細収容量算出と基本操作性向上  
**工数見積:** 3〜4 日  

#### 3.1.1 収容量計算パラメータ拡張

各ラックタイプにパラメータを追加する。

**ネスティングラック**
```javascript
nesting: {
  // 既存
  width: 1350, depth: 1200, height: 1700,
  // 追加パラメータ
  palletWidth: 1100,      // パレットサイズ幅 (mm)
  palletDepth: 1100,      // パレットサイズ奥行 (mm)
  stackLevels: 4,         // 段積み数
  spotsPerUnit: 1,        // 1連あたりスポット数
  // 算出式: totalPallets = count × spotsPerUnit × stackLevels
}
```

**パレットラック**
```javascript
pallet: {
  width: 2700, depth: 1100, height: 5000,
  bays: 2,                // 間口数 (1連あたり)
  levels: 4,              // 棚段数（GL含む）
  palletWidth: 1100,      // 対象パレット幅 (mm)
  palletDepth: 1100,      // 対象パレット奥行 (mm)
  beamHeight: 1200,       // 棚段ピッチ (mm)
  // 算出式: totalLocations = count × bays × levels
}
```

**軽量棚**
```javascript
shelf: {
  width: 900, depth: 450, height: 1800,
  shelves: 5,             // 棚板数
  divisionsPerShelf: 3,   // 1段あたり区画数
  // 算出式: totalLocations = count × shelves × divisionsPerShelf
}
```

#### 3.1.2 複数選択・コピー&ペースト

```
実装方針:
1. APP.selectedItems = [] (配列化)
2. Shift+クリック → selectedItems へ追加
3. Ctrl+A → 全選択
4. ゴムバンド選択（mousedown→mousemove→mouseup でボックス描画）
5. Ctrl+C → APP.clipboard = deep copy of selectedItems
6. Ctrl+V → clipboard を (offset + 100mm) にペースト
7. Delete → selectedItems を全削除
8. 描画: selectedItems の各アイテムにハンドル表示
```

#### 3.1.3 レイヤー管理

```
レイヤー定義:
- layer_rack: ラック類
- layer_obstacle: 障害物
- layer_zone: ゾーン（Phase 4）
- layer_annotation: 寸法・注釈

各レイヤーに:
- visible: boolean（表示/非表示）
- locked: boolean（操作ロック）
- opacity: number（透明度）
```

### Phase 2: 通路幅検出・色分け

**目的:** 消防法・フォークリフト作業安全基準に基づく通路判定  
**工数見積:** 4〜5 日  

#### 3.2.1 通路幅基準

| 通路種別 | 基準幅 | 表示色 | 根拠 |
|---------|--------|--------|------|
| 主通路（フォーク専用） | ≥3,500mm | 緑 | カウンター式フォーク通路 |
| 副通路（リーチ式対応） | ≥2,500mm | 黄 | リーチ式フォーク通路 |
| 歩行通路 | ≥1,200mm | 赤 | 労働安全衛生規則 第 542 条 |
| 違反 | <1,200mm | 濃赤（警告） | 通路確保義務違反 |

#### 3.2.2 通路検出アルゴリズム

```
アルゴリズム概要（スイープライン法）:

1. 水平方向スキャン:
   - Y 軸方向に 100mm ステップでスキャン
   - 各スキャンライン上でアイテム・障害物の X 区間を収集
   - 区間の隙間 = 通路候補
   - 隙間幅を計算 → 色分け閾値に対応付け

2. 垂直方向スキャン:
   - X 軸方向に 100mm ステップでスキャン
   - 同様に Y 方向の隙間を通路候補として収集

3. 通路オブジェクト生成:
   { x, y, width, height, type: 'main'|'sub'|'walk'|'violation' }

4. Canvas レンダリング:
   - 透過度 30% で通路幅に応じた色でオーバーレイ描画
   - 幅の数値を通路中央にラベル表示（例: "2,700mm"）

5. トグルボタンで表示/非表示切替
```

#### 3.2.3 通路サマリー表示

右パネルに「通路チェック」セクションを追加:
- 主通路数・平均幅
- 副通路数・平均幅
- 違反箇所数（赤で強調）
- 最小通路幅

### Phase 3: 障害物考慮自動配置

**目的:** 障害物・保全距離・既存ラックを避けた賢い自動配置  
**工数見積:** 4〜5 日  

#### 3.3.1 配置禁止ゾーンマップ

```
1. グリッドセル（100mm × 100mm）のビットマップ生成
   forbidden[y][x] = true/false

2. 禁止セル登録:
   - 倉庫壁から壁際距離以内
   - 全障害物の占有エリア
   - 各障害物の保全距離エリア
   - 既存ラックの占有エリア（同タイプのみクリア対象）

3. 配置候補探索:
   - 左上から右→下の順でグリッドスキャン
   - ラックサイズ分の矩形が全セル forbidden=false → 配置可能
   - 配置後にそのセルを forbidden=true に更新

4. 通路確保:
   - 各列後に aisle_width 分のセルを forbidden=true に設定
   - 行間も同様に row_gap 分を確保
```

#### 3.3.2 配置優先度オプション

- 「壁際優先」: 壁に沿って配置し中央を通路に
- 「中央優先」: 中央から配置
- 「ゾーン内配置」: 選択ゾーン内のみに配置（Phase 4 連携）

### Phase 5: 荷主向け提案書生成

**目的:** 荷主情報・物量データから倉庫設計・運営概算を自動生成  
**工数見積:** 5〜7 日  

#### 3.5.1 入力パラメータ

```javascript
proposal: {
  // 荷主基本情報
  clientName: string,        // 荷主名
  contractStartDate: string, // 契約開始日
  productType: string,       // 商材種別（アパレル/食品/日用品/他）

  // 在庫情報
  skuCount: number,          // SKU 数
  avgInventoryUnits: number, // 平均在庫数（個）
  avgInventoryPallets: number, // 平均在庫数（パレット）

  // 出荷情報
  dailyShipmentOrders: number, // 日次出荷件数
  dailyShipmentLines: number,  // 日次出荷行数
  dailyShipmentUnits: number,  // 日次出荷個数
  peakRatio: number,           // ピーク係数（例: 3.0）

  // 入荷情報
  dailyReceivingPallets: number, // 日次入荷パレット数
  receivingDaysPerWeek: number,  // 週次入荷日数

  // 荷主指定要件
  rackType: string,          // 優先ラックタイプ
  forkliftType: string,      // フォークリフト種別
  tempZone: string           // 温度帯（常温/冷蔵/冷凍）
}
```

#### 3.5.2 算出ロジック

```
必要保管面積:
  palletStorageArea = avgInventoryPallets × 1.1 (m²/パレット) × 1.2 (安全率)
  shelfStorageArea = skuCount / locationsPerM2 × 1.3

必要作業員数:
  pickingStaff = dailyShipmentLines / 200 (lines/人/日 標準)
  receivingStaff = dailyReceivingPallets / 50 (pallets/人/日 標準)
  peakStaff = ceil((pickingStaff + receivingStaff) × peakRatio / 0.7)

フォークリフト台数:
  forklifts = ceil(dailyReceivingPallets / 150) + ceil(dailyShipmentOrders / 300)

必要ラック数（パレットラック例）:
  requiredPalletRacks = ceil(avgInventoryPallets / (bays × levels))

総必要面積:
  totalArea = storageArea + workArea(30%) + facilitiesArea(10%)
```

#### 3.5.3 提案書 PDF 構成

```
表紙: プロジェクト名・荷主名・作成日・作成者
P.1 : 倉庫基本仕様（面積・天高・ゾーン構成）
P.2 : 設備計画（ラック数・フォーク台数・什器）
P.3 : 人員計画（通常時・ピーク時）
P.4 : レイアウト平面図（Canvas 画像）
P.5 : KPI 目標値（出荷精度 99.9%/生産性指標）
P.6 : 費用概算（設備投資・月次運営費）
```

### Phase 6: ルールベース AI レイアウト提案

**目的:** 物流設計知識をルール化した自動レイアウト生成  
**工数見積:** 7〜10 日  

#### 3.6.1 設計ルールセット

```
R-001: 入荷エリアはドックに隣接配置
R-002: 出荷エリアはドックに隣接（入荷と分離）
R-003: 検品エリアは入荷エリアと出荷エリアの中間
R-004: 主通路は倉庫中央またはゾーン境界に配置
R-005: 消火栓・分電盤の保全距離を最優先で確保
R-006: ピッキングエリアは出荷エリアに近接
R-007: パレットラックは主通路沿いに配置
R-008: 軽量棚はピッキングエリアに集約
R-009: ネスティングラックは入荷・出荷エリア近傍
R-010: フォーク充電エリアは通路終端に配置
```

#### 3.6.2 提案フロー

```
1. 荷主情報 (Phase 5) から必要ゾーン面積を算出
2. ゾーン配置最適化（制約充足問題として解く）
   - 優先順位: ドック周辺 → 主通路 → 各ゾーン → ラック
3. 各ゾーン内にラック自動配置（Phase 3 アルゴリズム）
4. 通路幅チェック（Phase 2）→ 違反あれば再計算
5. スコア評価（動線効率・面積利用率・コンプライアンス）
6. 上位 3 案をユーザーに提示
```

## 4. アーキテクチャ設計方針

### 4.1 コード構成

単一 HTML ファイルの保守性を高めるため、論理的なモジュール分割を `// === MODULE: xxx ===` コメントで明示する。

```
=== MODULE: CONFIG ===      定数・マスタデータ
=== MODULE: STATE ===       APP オブジェクト（状態管理）
=== MODULE: STORAGE ===     LocalStorage CRUD
=== MODULE: CANVAS ===      描画ロジック
=== MODULE: ITEMS ===       ラック操作
=== MODULE: ZONES ===       ゾーン管理（Phase 4）
=== MODULE: CALC ===        収容量・面積計算
=== MODULE: CORRIDOR ===    通路幅検出（Phase 2）
=== MODULE: AUTOPLACE ===   自動配置（Phase 3）
=== MODULE: PROPOSAL ===    提案書生成（Phase 5）
=== MODULE: EXPORT ===      PNG/PDF/Excel エクスポート
=== MODULE: UI ===          イベントハンドラ・UI 制御
=== MODULE: 3DVIEW ===      Three.js 3D ビュー
```

### 4.2 状態管理方針

```javascript
const APP = {
  // --- 倉庫設定 ---
  warehouse: { name, width, depth, height },

  // --- 配置データ ---

  zones: [],          // ゾーン（Phase 4 追加）

  tool: 'select',     // select / pan / place

  clipboard: [],      // コピーバッファ

  // --- 表示フラグ ---
  showGrid: true,
  showDimensions: true,
  showHeatmap: false,

  history: [],
```

### 4.3 データバージョニング方針

LocalStorage の JSON に `version` フィールドを設け、スキーマ変更時は自動マイグレーションを行う。

```javascript
const MIGRATIONS = {
  1: (data) => data,  // v1 (現行)
  2: (data) => {
    // Phase 1: ラックパラメータ拡張マイグレーション
    data.items.forEach(item => {
      if (item.type === 'pallet' && !item.params) {
        item.params = { bays: 2, levels: 4 };
      }
    });
    data.zones = data.zones || [];
    return data;
  }
};
```

### 4.4 パフォーマンス方針

| 対象 | 方針 |
|------|------|
| Canvas 再描画 | requestAnimationFrame でスロットリング |
| 通路検出 | Web Worker で非同期実行（ブロッキング防止） |
| 自動配置 | バックグラウンド計算 → 完了後に一括描画 |
| LocalStorage 書込 | デバウンス 500ms |
| 3D シーン | ラック 500 個超は LOD 切替 |

## 5. 物流コンサルタント視点での追加提案機能

3PL 物流センター立ち上げ支援の実務経験に基づく追加提案機能。各機能は独立したフェーズとして実装可能。

---

### 提案 01: 作業動線シミュレーション

**概要:** 入荷→保管→ピッキング→出荷の作業動線を矢印で可視化し、交差・逆行を検出する。

**詳細:**
- ゾーン間の標準フロー（入荷→検品→保管→ピッキング→仕分→出荷）を矢印で描画
- 動線の交差回数をカウント（多いほど危険）
- 動線長（移動距離）を算出し、オペレーションコストを試算
- 「往復動線スコア」として数値化（低いほど良）

**期待効果:** ピッキング生産性 10〜20% 改善

---

### 提案 02: 重量床荷重チェック

**概要:** ラック配置エリアの床荷重（kN/m²）を計算し、建物仕様との適合性を判定。

**詳細:**
- 各ラックの最大積載重量（kg）をマスタに登録
- 配置エリアのフットプリントで荷重（kN/m²）を計算
- 建物の床荷重許容値（デフォルト: 1.5t/m²）と比較
- 超過エリアを赤でハイライト
- 床補強費用の概算出力

**期待効果:** 物件選定時の建物適合性リスク低減

---

### 提案 03: フォークリフト動線・旋回半径チェック

**概要:** フォークリフトの旋回半径を考慮した通路交差点の安全性チェック。

**詳細:**
- フォークリフト機種別に旋回半径を登録（リーチ式: 1,600mm、カウンター3.5t: 2,500mm）
- 主通路と副通路の交差点に旋回スペース円を描画
- 旋回半径が確保できない交差点を警告表示
- 鏡・安全標識の推奨設置位置をマーク

**期待効果:** 構内事故リスク低減、労災防止

---

### 提案 04: 在庫回転率別ロケーション配置最適化（ABC 分析）

**概要:** 商品の出荷頻度（A/B/C ランク）に基づき、ピッキング効率を最大化するロケーション配置を提案。

**詳細:**
- A ランク（出荷頻度上位 20%）: 出荷口近傍・腰高ロケーション
- B ランク（次の 30%）: 中間エリア
- C ランク（残り 50%）: 奥・高所
- SKU 数・出荷比率を入力 → ゾーン別必要ロケーション数を算出
- レイアウト上にゾーンカラーマップで可視化

**期待効果:** ピッキング歩行距離 30〜40% 削減

---

### 提案 05: 非常口・避難経路チェック

**概要:** 消防法に基づく避難経路の確保状況を自動チェック。

**詳細:**
- 非常口を障害物タイプに追加（`emergency_exit`）
- 非常口から任意地点までの最短経路をダイクストラ法で算出
- 最大避難距離（消防法: 60m）超過エリアを赤でハイライト
- 避難経路（通路）の最小幅 1,200mm チェック
- 消防設備（消火器・スプリンクラーヘッド）の設置推奨位置を表示

**期待効果:** 消防検査対応、火災リスク低減

---

### 提案 06: 温度帯ゾーン管理

**概要:** 常温・冷蔵・冷凍の温度帯ゾーンを管理し、設備・光熱費を算出。

**詳細:**
- ゾーンに温度帯属性（常温/10℃/5℃/-25℃）を付与
- 温度帯境界に断熱壁・エアカーテンの要否を判定
- ゾーン面積から冷凍冷蔵設備の概算費用を算出
- 電気代・CO₂ 排出量の年間試算
- 荷主向けコールド設備費用を提案書に自動反映

**期待効果:** 多温度帯センター設計の効率化

---

### 提案 07: IoT センサー配置計画

**概要:** 倉庫管理の IoT 化に向けた各種センサーの配置計画ツール。

**詳細:**
- センサータイプ: RFID リーダー、カメラ（AI 検品）、ビーコン、温湿度センサー、人感センサー
- 通信カバレッジ範囲を円で描画（例: RFID 6m）
- 全エリアのカバー率を算出（目標 100%）
- 死角エリアを赤でハイライト
- センサー数・配線距離から設備費用概算

**期待効果:** WMS/IoT 連携設計の効率化

---

### 提案 08: 季節変動・スケーラビリティ計画

**概要:** 繁忙期の在庫増・出荷増に対応するレイアウト拡張計画を可視化。

**詳細:**
- 現状レイアウトを「通常時」として保存
- ピーク係数（例: 3.0×）入力でピーク時の必要ラック数を算出
- 追加配置できる余剰スペースをハイライト
- 「増設シナリオ」として別レイアウトを保存・比較
- 増設コスト・対応可能ピーク物量を提案書に反映

**期待効果:** 繁忙期の倉庫逼迫・追加費用の事前対策

---

### 提案 09: 多拠点レイアウト比較・テンプレート管理

**概要:** 複数倉庫のレイアウトを比較・評価し、ベストプラクティスをテンプレート化。

**詳細:**
- 複数レイアウトを IndexedDB に保存（LocalStorage 容量制限回避）
- レイアウト一覧画面（サムネイル表示）
- 面積利用率・収容効率・通路適合率でランキング表示
- 優良レイアウトを「テンプレート」として登録・再利用
- JSON エクスポート/インポートで拠点間共有

**期待効果:** 新規拠点立ち上げ工数 50% 削減

---

### 提案 10: コスト算出・投資対効果（ROI）試算

**概要:** ラック・フォーク・什器の導入費用と運営コストから ROI を自動試算。

**詳細:**
- 設備単価マスタ（ラック 1 連: 50,000 円〜、フォーク: 2,000,000 円〜）
- 配置されたラック数・台数から設備投資総額を算出
- 月次固定費（賃料・人件費・光熱費）を入力 → 損益分岐点算出
- 荷主出荷数・単価から月次売上を試算
- ROI・投資回収期間を計算
- 提案書（Phase 5）の財務ページに自動反映

**期待効果:** 荷主への数字根拠ある提案、受注率向上

---

### 提案 11: 作業標準時間（ST）自動設定

**概要:** 物流業務の標準時間（Standard Time）データベースと連携した生産性試算。

**詳細:**
- 業務別 ST マスタ（パレット入荷: 3 分/枚、ピッキング: 0.5 分/行 等）
- 物量データから 1 日の必要工数（人時）を算出
- ラックタイプ別の作業効率係数（軽量棚 1.0 / パレットラック 0.8 等）
- レイアウト変更時に生産性への影響を自動試算
- 採用計画・シフト計画の基礎データとして出力

**期待効果:** 採用計画・見積精度向上

---

### 提案 12: マルチテナント対応（複数荷主混在）

**概要:** 単一倉庫内で複数荷主のエリアを管理するマルチテナント機能。

**詳細:**
- 荷主別にゾーン・ラックをカラーコーディング
- 荷主別面積・ラック数・利用率を集計
- 荷主別の請求根拠（m² × 単価 + ラック数 × 単価）を自動生成
- エリア割り当て変更のシミュレーション（増床/縮小）
- 荷主別レポート PDF の個別出力

**期待効果:** マルチテナント倉庫の管理効率化・請求精度向上
